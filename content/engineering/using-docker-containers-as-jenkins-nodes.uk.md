Ця стаття описує використання контейнерів Docker як окремих нод для системи неперервної інтеграції (у даному випадку Jenkins). Кому лінь читати: [tl;dr репозиторій на GitHub](https://github.com/rrader/docker-jenkins-slave).

Для збірки нашого проєкту в RPM та DEB пакети ми використовуємо Jenkins, під який виділено окрему машину.

![Дистрибутиви](/images/docker-jenkins-nodes/image-01.png)

Спочатку ми збирали наш проєкт тільки для CentOS 6. Далі додалася підтримка CentOS 5, і виявилося, що жорсткі залежності від конкретних версій бібліотек не дозволяють запускати одні й ті самі бінарники під різними версіями дистрибутива — знадобилася збірка різних RPM. Спочатку це вирішувалося додаванням у Jenkins ноди з CentOS 5, якою слугувала звичайна віртуалка на VirtualBox. Згодом додалася підтримка SUSE, а потім і Debian.

Кількість оперативної пам'яті не гумова, а використання повноцінних віртуальних машин суто для компіляції та пакування — це невиправданий оверхед. Тому було вирішено переписати скрипти з використанням Docker.

Використовуючи Jenkins для CI, можна підключати ноди з потрібними операційними системами кількома шляхами:
- Орендувати окремі машини/сервери та тримати їх увімкненими.
- Використовувати класичну віртуалізацію (гіпервізори KVM, VirtualBox тощо).
- Контейнери (LXC, Docker, jail).

Переваги контейнерів перед віртуальними машинами тут очевидні: оперативна пам'ять спільна та динамічно виділяється за потребою, а велика кількість запущених контейнерів не просаджує систему. При цьому Docker додає важливі моменти:
- Для збірки проєкту запускається суто скрипт збірки й нічого зайвого, тоді як у VM працюють усі системні демони, що з'їдає ресурси хоста.
- «Дешеве» створення ізольованих клонів оточення для кожної задачі.

## Docker як нода в Jenkins

Для Jenkins-слейва нам потрібні:
1. Java
2. Точка входу — SSH-сервер
3. Інструменти для збірки проєкту

Точка входу потрібна для запуску процесу в Docker та збереження стану файлової системи в рамках сесії збірки (LXC зазвичай використовує `init`, але нам ціла ОС не потрібна). Оскільки Jenkins однаково спілкується з нодами через SSH, цей демон і є точкою входу.

Для конфігурації образів використовується Dockerfile. У репозиторії **[rrader/docker-jenkins-slave](https://github.com/rrader/docker-jenkins-slave)** доступні готові правила збірки для:
- CentOS 5
- CentOS 6
- SUSE 12
- Debian 6

Пул-реквести з новими системами та покращеннями скриптів вітаються!

## Збірка та використання

Передбачається, що у вас уже встановлені Docker та Jenkins.

1) Встановіть у Jenkins [Swarm Plugin](https://wiki.jenkins-ci.org/display/JENKINS/Swarm+Plugin) (він дозволяє слейвам автоматично реєструватися на мастері через API).

2) Клонуйте репозиторій:
```bash
git clone https://github.com/rrader/docker-jenkins-slave.git
cd docker-jenkins-slave
```

3) Перейдіть у папку з правилами для потрібної ОС та зберіть образ:
```bash
cd centos6
sudo bash build.sh
```

4) Коли образ збереться, ви можете запускати скільки завгодно нод цього типу:
```bash
sudo bash add_slave.sh SlaveName
```

Після виконання цієї команди нова нода з'явиться в Jenkins. Для її використання достатньо вказати в конфігурації збірки відповідний тег, наприклад `docker-centos6.4`. Список усіх підтримуваних тегів зібрано у [Wiki репозиторію](https://github.com/rrader/docker-jenkins-slave/wiki/Tags).
